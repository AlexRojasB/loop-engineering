# What You Are Deciding

"The contract" means THE FROZEN TEST CODE shown above - nothing else.
The authoritative requirement is never in question and is never
rewritten. If you decide the contract is defective, those TEST METHODS
are discarded and regenerated by another agent. So "the tests are
defective" and "the contract is defective" are the same verdict here:
CONFIRM. There is no third answer for reporting a bad test.

CONFIRM means: no implementation of the authorized production files,
however written, could make the cited test(s) pass while conforming to
the authoritative requirement above.

REJECT means anything else.

Do not reason about what test-driven development "usually implies", or
about tests being authoritative in general. In this decision the
requirement is authoritative and the tests are the artifact under
review. If your trace of the cited test concludes that it must fail for
the code as shown and the requirement as written, the answer is CONFIRM.

# Rules

1. "The feature is not implemented yet" is NEVER a defect in the
   contract. Tests are written first and are supposed to fail until the
   production code exists. If the cited test would pass once the
   requested behavior is correctly implemented, REJECT.

2. "The implementation is hard", "the test is awkward", "the test also
   depends on other behavior", or "I would have written the test
   differently" are NOT defects. REJECT.

3. CONFIRM only on a demonstrable contradiction, such as:
   - the test requires behavior the authoritative requirement forbids,
     or contradicts what it states;
   - the test operates on an object, identifier or handle that the code
     path under test can never have been given (identity/provenance);
   - the test requires an existing, unchanged production API to behave
     in a way it demonstrably does not, and the requirement does not ask
     for that API to change;
   - the test asserts two things that cannot both hold;
   - satisfying the test would require modifying files the agent is not
     authorized to change, or would break the stated requirement.

4. Verify the contradiction yourself against the material above. Trace
   the cited test line by line. If the challenge's stated reason is
   wrong but a different real contradiction exists, CONFIRM and say
   what the real one is.

5. Judge the code AS SHOWN. Do not rescue a contract by supposing that
   some class you cannot see might behave differently, and do not
   condemn one that way either. If a decisive fact depends on code that
   is not shown above, REJECT and name the file the report should have
   cited instead.

6. Do not hedge. If your own analysis establishes the contradiction for
   the code as shown, you MUST answer CONFIRM. A verdict of REJECT
   qualified by "unless", "if the contract allows", or "assuming
   something else were true" is wrong: either the contradiction holds
   for the code as shown, and the answer is CONFIRM, or it does not, and
   the answer is REJECT.

7. If, after tracing the test, you cannot establish the contradiction,
   REJECT. Genuine uncertainty means the contract stands.

8. Do not propose a replacement contract. Do not rewrite tests. Do not
   suggest that the agent report the problem some other way: this is
   the only channel, and your verdict is the decision.

# Output

Return ONLY this JSON object:

{{"decision": "CONFIRM", "reasons": ["..."]}}

or

{{"decision": "REJECT", "reasons": ["..."]}}

For an identity or provenance claim, `reasons` must name the two
instances involved and state whether they are the same one.

`reasons` is AT MOST FIVE short strings holding your CONCLUSIONS. Not
your deliberation: no exploratory notes, no "wait", no questions, no
alternatives you considered and dropped, no restating the rules. For
CONFIRM, state the contradiction and the exact test line that proves it.
For REJECT, state what the agent must do instead.

Do the reasoning below silently. Emit only the JSON object.

# Procedure

Work through this before answering:

1. Which exact line of the cited test fails, and what does it require?

2. What value or object does that line operate on, and where did it come
   from? Follow its provenance through the production code shown, and be
   exact about INSTANCES, not just types or names:

   - Which instance holds the value the test passes in?
   - Which instance, if any, can the code under test actually reach?
   - Are those the same instance?

   Where production code generates a value PER INSTANCE - an id, handle,
   key, token or timestamp created inside a constructor or factory - two
   objects built from equal inputs do NOT share it. "An equivalent object
   was registered" is not the same as "this object's value can be found".
   A registered copy with a different generated id is a different object
   as far as any lookup by that id is concerned.

3. Could ANY correct implementation of the authorized production files
   make that line succeed while honoring the authoritative requirement?
   Say concretely how, or say why it is impossible.

4. If yes -> REJECT. If no -> CONFIRM.
